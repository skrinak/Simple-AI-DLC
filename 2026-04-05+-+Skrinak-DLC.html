The Skrinak-DLC: An AI-Driven Development Lifecycle for Enterprise Teams

A simpler, memorable, and immediately actionable alternative to complex AI development methodologies, built on lessons from the Claude Code architecture leak, battle-tested context engineering patterns, and the goals of AWS's AI-DLC.

Detailed process diagram: Skrinak-DLC Process Diagram

The Problem

The AWS AI-DLC is right about what matters: AI should drive development, not assist it. Humans validate, not babysit. Complex systems demand rigor. But its implementation: 9 workflow steps, mob rituals, formal Units and Bolts, DDD-first mandates, is too heavy for any organization to actually adopt. Teams read it, nod, and go back to prompting ChatGPT.

Meanwhile, the Claude Code source leak revealed something important: the most successful AI agent in production ($2.5B run rate) runs on twelve boring engineering primitives: tool registries, permission tiers, crash recovery, token budgets. Not glamorous. Not complex. Just disciplined plumbing.

The Skrinak-DLC takes the goals of the AI-DLC, strips the ceremony, and rebuilds with these primitives as the foundation. It maps cleanly to the AWS AI stack: Kiro for spec-driven Inception, Amazon Bedrock as the model layer, Strands Agents for building agents that embody the primitives, and AgentCore for operating them in production. It is opinionated. It is simple. It works.

Ten Tenets

Tenets are not guidelines. They are load-bearing decisions made in advance so your team doesn't relitigate them every sprint.

  1. AI drives, humans decide. AI proposes architecture, decomposes work, generates code, and runs tests. Humans set intent, validate output, and own the consequences. The agent is the engine. You are the steering wheel.

  2. Context is the product. A well-structured CLAUDE.md, a clear PRD, and a disciplined task list produce better software than a brilliant developer with a vague prompt. Invest in context before you invest in code.

  3. Plan the work, then work the plan. No code is written until requirements are documented (PRD), tasks are decomposed, and dependencies are mapped. This is not waterfall, it is the minimum structure required for an AI agent to do useful work without hallucinating scope.

  4. Agents crash. Build for it. Session persistence, workflow checkpoints, and token budgets are not nice-to-haves. They are the difference between a product and a demo. Save state obsessively. Resume gracefully.

  5. Permissions are architecture. Every tool the agent can invoke must be classified by risk: read-only, mutating, or destructive. Every destructive action requires explicit human approval. No exceptions. No shortcuts.

  6. Clear early, clear often. Context rot and catastrophic forgetting are the two most common failure modes in AI-driven development. The fix is disciplined: clear context at 80% capacity, between phases, and before complex problems. Reload from your source of truth.

  7. Small tasks, fast cycles. Every task should be completable in a single agent session. If it takes more than 30 minutes or touches more than 5 files, break it down. This is not a suggestion, it is a constraint that prevents compounding errors.

  8. Verify the work and the harness. Two levels of verification: (1) Did the agent complete this task correctly? (2) Did my changes to the development environment break any guardrails? Both matter. The second one is the one teams forget.

  9. Eighty percent plumbing. Building with AI agents is 80% non-glamorous infrastructure: registries, logging, permissions, crash recovery, and 20% model interaction. Teams that skip the plumbing build demos. Teams that invest in it build products.

  10. Complexity is debt with interest. Start with a single agent. Add coordination only when you have evidence it's needed. The most common failure mode in agentic systems is overengineering: building multi-agent orchestration before your sessions can survive a crash.

Three Phases

The Skrinak-DLC preserves the AI-DLC's three phases, Inception, Construction, Operations, but strips each to its essential actions. No mob rituals. No formal artifacts beyond what the agent needs to do its job.

The AWS Stack

Four AWS services map directly to the three phases. Each handles a different layer of the lifecycle:

Layer AWS Service Role in the Skrinak-DLC
Model Amazon Bedrock Foundation model access: Claude, Nova, and others. The inference engine underneath every phase.
Inception Kiro Spec-driven IDE that generates requirements, design docs, and task lists before a line of code is written.
Construction Strands Agents Open-source SDK for building agents with tool registries, steering hooks, and session management: the 12 primitives in code.
Operations AgentCore Managed runtime for deploying agents at scale: session isolation, identity federation, Cedar policy enforcement, and observability.

These are not alternatives to each other. They are layers. Bedrock provides the models. Kiro plans the work. Strands builds the agents. AgentCore runs them in production. The Skrinak-DLC tenets and primitives govern how you use all four.

Phase 1: Inception

Goal: Transform a business intent into a structured, AI-consumable plan.

What happens:

  • A human states the intent: what the system should do and why.
  • The AI acts as senior product manager: it asks clarifying questions, identifies personas, proposes user stories, flags risks, and recommends architecture.
  • The output is a PRD (Product Requirements Document) built through 4 iterative rounds:
    • Round 1, Foundation: Personas, user journeys, high-level architecture
    • Round 2, Technical depth: Infrastructure, data flows, security model
    • Round 3, Implementation plan: Environments, testing strategy, monitoring
    • Round 4, Task decomposition: Atomic tasks, parallel execution opportunities, verification criteria

In Claude Code:

# Start a new project
/init

# Use the PRD skill to drive interactive requirements gathering
# The skill walks through all 4 rounds, producing PRD.md

In Kiro:

Kiro's spec-driven workflow is purpose-built for this phase. Where Claude Code uses a PRD skill, Kiro makes Inception a first-class IDE feature:

# Create a new spec in Kiro
# Kiro generates three artifacts in .kiro/specs/[feature-name]/

requirements.md   # User stories with EARS notation acceptance criteria
design.md         # Architecture, sequence diagrams, data flow, testing strategy
tasks.md          # Sequenced, dependency-mapped implementation tasks

Kiro's steering files (.kiro/steering/) serve the same role as CLAUDE.md: product.md defines purpose and users, tech.md defines frameworks and constraints, structure.md defines file organization. The constitution concept is the same; the file names differ.

The PRD is not a formality. It is the single document that prevents the agent from hallucinating scope, inventing requirements, or building the wrong thing. A 2-hour investment in the PRD saves 20 hours of rework.

What the AI-DLC gets right that we keep:

  • AI initiates the conversation, not the human. The agent asks: "Who are the primary users? What are the non-functional requirements? What compliance frameworks apply?" You answer.
  • Design techniques (DDD, event-driven architecture) are embedded in the process, not left to the developer to remember.
  • Every requirement traces forward to a task and backward to a business intent.

What we drop:

  • Mob Elaboration rituals. The PRD skill (Claude Code) or spec workflow (Kiro) handles this interactively.
  • Formal "Units" and "Bolts" terminology. Tasks are tasks.
  • PRFAQ as a required artifact. Optional if your organization uses them.

Phase 2: Construction

Goal: Convert the PRD into working, tested, deployable code.

What happens:

  • The PRD is converted into a task list, an ordered, dependency-aware checklist of atomic work items.
  • Each task follows a mandatory sequence: search existing code → review constraints → security review → implement → test → lint → commit.
  • The AI executes tasks one at a time, within a single focused session per task.
  • Context is actively managed: clear between tasks, reload CLAUDE.md and task state, continue.

In Claude Code:

# Generate task list from PRD
# Each task gets: description, verification criteria, dependencies, 
# parallel markers, and CLAUDE.md constraint references

# Execute tasks with disciplined context management
# Between tasks:
/clear
# Then reload context:
# "Read CLAUDE.md, README.md, tasks.md, and .env. Resume from task N."

The construction cycle for each task:

┌─────────────────────────────────────┐
│  1. Read CLAUDE.md (constraints)    │
│  2. Read task from tasks.md         │
│  3. Search existing code first      │
│  4. Implement (match patterns)      │
│  5. Test                            │
│  6. Lint / typecheck                │
│  7. Mark task complete              │
│  8. /clear if context > 80%        │
└─────────────────────────────────────┘

Key rules:

  • Never modify code without first reading every file that imports or calls the target.
  • Match existing patterns. The codebase is the style guide.
  • If a task is blocked, document why and move to the next unblocked task.
  • Never batch tests at the end. Every task includes its own verification.

Strands defaults to Bedrock but supports 13+ model providers. The agent code is portable; the operational layer is where AWS-specific choices matter.

Phase 3: Operations

Goal: Deploy, monitor, and maintain the system in production.

What happens:

  • Infrastructure-as-Code is generated from the architecture decisions made in Inception.
  • Deployment follows the security model defined in CLAUDE.md (region constraints, encryption standards, IAM policies).
  • The AI monitors telemetry, proposes scaling actions, and integrates with incident runbooks.
  • Post-deployment verification confirms that the system meets the NFRs defined in the PRD.

The Twelve Primitives

These are the engineering primitives revealed by the Claude Code architecture leak. They are organized into two tiers: Day One (non-negotiable from the start) and Operational Maturity (add as the system scales). Each primitive maps to concrete Claude Code capabilities and ContextEng patterns.

Day One: Non-Negotiables

1. Tool Registry with Metadata-First Design

Every capability the agent can use is declared in a searchable registry before any code runs.

Claude Code maintains two parallel registries: 207 user-facing commands and 184 model-facing tools. Each entry carries a name, source, and description. Implementations load on demand.

For your team: Your CLAUDE.md defines what tools are available and what constraints apply. MCP servers extend the registry at runtime. Skills and slash commands are registered capabilities with metadata: name, description, allowed context. If your agent can't list its own capabilities without executing them, you don't have a registry. You have a bag of scripts.

2. Permission System with Trust Tiers

Not all tools carry the same risk. Classify risk. Apply different approval requirements per tier.

Claude Code segments capabilities into three trust tiers: built-in (highest trust, always available), plug-in (medium trust, can be disabled), and skills (lowest trust, user-defined). The Bash tool alone has an 18-module security architecture, from pre-approved command patterns to destructive command warnings to sandbox termination.

For your team: Your .claude/settings.json defines exactly which tools and commands are permitted. CLAUDE.md encodes your security posture: encryption standards, IAM policies, compliance frameworks. Every destructive action (rm, DROP TABLE, force-push) requires explicit human approval. This is not paranoia. This is what separates a $2.5B product from a notebook demo.

3. Session Persistence That Survives Crashes

The session is not just conversation history. It is a recoverable state: messages, token usage, permissions, and configuration.

Claude Code persists full sessions as JSON. After a crash, it reconstructs the complete agentic engine: transcript, counters, tool state, permission decisions.

For your team: This maps to the three tiers of memory:

Tier Analogy Claude Code Feature Purpose
CLAUDE.md Constitution Project instructions loaded every session Immutable principles, constraints, architecture
Memory files Case law .claude/memory/ persistent storage Lessons learned, user preferences, project context
In-conversation Live testimony Active session context Current task state, corrections, discoveries

Use /resume to restore session state. Use /clear + context reload to start fresh without losing institutional knowledge. The constitution survives every crash.

4. Workflow State vs. Conversation State

Resuming a conversation is not the same as resuming a workflow. Track both.

A conversation transcript answers "what have we said?" A workflow state answers "what step are we in, what side effects have happened, and is this safe to retry?"

For your team: Your tasks.md is your workflow state. Each task has a status (pending, in-progress, complete, blocked), verification criteria, and dependency markers. When you /clear and reload, the conversation resets but the workflow persists in the file. This is why task files are sacred: they are your checkpoint system.

5. Token Budget Tracking

Every turn calculates projected token usage. If the projection exceeds the budget, execution stops before the API call is made.

Claude Code defines hard limits on tokens per conversation and maximum turns. It auto-compacts when thresholds are hit.

For your team: The rule is simple: clear at 80% capacity. Use /compact for automatic context compression. Use /clear for a hard reset. The 30-minute / 5-file task constraint from Tenet 7 is a budget mechanism, it keeps individual tasks within a single context window.

6. Structured Streaming Events

Every streaming event is an opportunity to communicate system state, not just text output.

Claude Code emits typed events: message_start, tool_match, command_match, and crash events with structured reasons. This is the "stream of thought" that lets humans intervene before the agent goes off-track.

For your team: Watch the stream. When you see the agent heading in the wrong direction (wrong file, wrong approach, wrong tool) interrupt immediately. A 5-second correction in-stream saves a 5-minute rollback. The stream is not decoration. It is your steering wheel.

7. System Event Logging

The conversation transcript tells you what the agent said. The event log tells you what it did.

Claude Code maintains a separate history of system events: context loaded, registry initialization, routing decisions, execution counts, permission denials.

For your team: CLAUDE.md should require that every significant action is logged. In an enterprise context, this is your audit trail. When compliance asks "what did the AI do and why?", the answer lives in the event log, not the chat transcript.

8. Two-Level Verification

Level 1: Did the agent complete the task correctly? Level 2: Did changes to the harness break any guardrails?

Claude Code includes verification tests for both: task-level correctness checks and harness-level guardrail tests (e.g., "do destructive tools still require approval after this change?").

For your team: Every task in tasks.md includes verification criteria. But also: when you modify CLAUDE.md, update .claude/settings.json, or change MCP server configuration, verify that your security posture hasn't degraded. The harness is infrastructure. Test it like infrastructure.

Operational Maturity: Scale When Ready

9. Tool Pool Assembly

A general-purpose agent with 184 tools doesn't load all of them every session. It assembles a session-specific pool based on context.

Claude Code dynamically selects tools based on mode flags, permission context, and deny lists.

For your team: Not every task needs every MCP server. Install MCP servers when needed, remove them after. A code review task doesn't need the database MCP. A deployment task doesn't need the browser MCP. Leaner tool pools mean faster execution and fewer permission risks. As the ContextEng pattern warns: MCP servers degrade efficiency; install only when needed, remove immediately after.

10. Transcript Compaction

Automatically compress conversation history after a configurable threshold. Keep recent entries. Discard older ones.

Claude Code tracks whether compacted transcripts have been persisted to avoid data loss.

For your team: This is the /compact command in practice. But the deeper lesson is architectural: design your workflow so that no single conversation needs the full history. The PRD carries forward requirements. The task list carries forward progress. CLAUDE.md carries forward constraints. The conversation itself can be ephemeral because the important state lives in files.

11. Permission Audit Trail

Permissions are not a boolean gate. They are a first-class object you can query, replay, and audit.

Claude Code builds three separate permission handlers: interactive (human-in-the-loop), coordinator (multi-agent orchestration), and swarm worker (autonomous execution managed by an orchestrator).

For your team: Start with interactive permissions: a human approves every destructive action. As your team matures and trust is established, you can define pre-approved patterns in .claude/settings.json. But the audit trail never goes away. Every permission decision, granted or denied, should be logged with enough context to replay it. This is non-negotiable for enterprise compliance.

12. Agent Type System

Don't spawn agents randomly. Constrain roles sharply into observable types with specific tools and behavioral limits.

Claude Code defines six built-in agent types: Explore (read-only, cannot edit), Plan (designs approaches, cannot execute), Verify (checks work, cannot modify), Guide (answers questions), General Purpose (full capabilities), and Status Line Setup (specialized configuration). Each has its own prompt, allowed tools, and constraints.

For your team: When your work requires multiple agents, define their types explicitly. An agent reviewing code should not be able to edit it. An agent planning architecture should not be able to deploy it. Constrained roles prevent cascading errors and make multi-agent systems auditable. Start with a single general-purpose agent (Tenet 10). Add specialized types only when you have evidence that role separation improves outcomes.

The Memory Architecture

The three-tier memory model is the Skrinak-DLC's answer to both the AI-DLC's "context memory" concept and the Claude Code leak's session persistence primitive. It is the mechanism by which institutional knowledge survives across sessions, team members, and project phases.

Tier 1: The Constitution (CLAUDE.md)

CLAUDE.md is loaded at the start of every session. It contains the immutable truths about your project:

  • Constraints: What the agent must never do (e.g., never hardcode mock data, never deploy outside approved regions, never commit without explicit request)
  • Standards: Code patterns, typing requirements, encryption standards
  • Architecture: System topology, service boundaries, approved AWS services
  • Security posture: Compliance frameworks, encryption requirements, IAM policies

This file is version-controlled. Changes require the same review process as production code. It is the constitution: amended rarely, followed always.

Tier 2: Case Law (Memory Files)

Memory files in .claude/memory/ accumulate lessons learned across sessions:

  • User memories: Role, expertise, preferences (e.g., "senior backend engineer, new to React, frame frontend explanations in backend terms")
  • Feedback memories: Corrections and confirmations (e.g., "integration tests must hit a real database, not mocks, prior incident where mock/prod divergence masked a broken migration")
  • Project memories: Active initiatives, deadlines, stakeholder decisions
  • Reference memories: Pointers to external systems (e.g., "pipeline bugs are tracked in Linear project INGEST")

Case law evolves. It captures the gap between what the constitution says and what the team has learned in practice.

Tier 3: Live Testimony (In-Conversation)

The active session context: current task, recent file reads, corrections made in real time. This is ephemeral by design. When the context degrades, you /clear and reload Tiers 1 and 2. Nothing of lasting value is lost because lasting value lives in files, not in conversation history.

What This Is Not

  • Not a framework to install. It is a set of tenets and practices. Your CLAUDE.md, your PRD template, your task list format: these are the implementation.
  • Not model-specific. The tenets apply regardless of which LLM you use. Claude Code, Kiro, Strands, and AgentCore are one instantiation on AWS. The primitives are universal.
  • Not a replacement for engineering judgment. The AI drives. You decide. If the agent proposes something that violates your security model, your compliance requirements, or your common sense, you stop it. That is the job.

The Skrinak-DLC: Ten tenets. Twelve primitives. Three phases. One constitution. Plan in Kiro, build with Strands, run on AgentCore, powered by Bedrock. Ship enterprise software with AI agents that don't just work, they work safely, recoverably, and at scale.
